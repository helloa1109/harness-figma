# 디자인 QA 자동화 프로젝트

## 한 줄 요약

**디자이너가 디자인을 수정하면, 코드도 자동으로 수정되고, 그게 시안과 일치하는지 자동으로 검증되는 워크플로우.**

## 왜 만들었나

기존 디자인 → 개발 협업의 고질병:

- 디자이너가 피그마를 수정하면 → 캡처를 떠서 슬랙에 붙이고 → 개발자에게 “여기 padding 4px만 줄여주세요” 요청 → 개발자가 수동 반영 → 다시 QA → 또 수정
- 디자인 토큰이 바뀌었는데 코드에 반영 안 됨 → 시안과 코드의 미세한 불일치가 누적
- 컴포넌트마다 하드코딩된 색상/사이즈가 흩어져 있어 일괄 수정 불가

이 템플릿은 **Figma MCP**와 **Claude Code**를 연결해, 위 과정을 자동화한다.

## 핵심 아키텍처

```
   ┌──────────────┐   MCP    ┌─────────────────┐   파일 작업   ┌────────────┐
   │              │ ───────► │                 │ ───────────► │            │
   │  Figma 시안  │          │   Claude Code   │              │  로컬 코드  │
   │              │ ◄─────── │  (에이전트 위임) │ ◄─────────── │            │
   └──────────────┘ 토큰/이미지└─────────────────┘   훅 검증   └────────────┘
                                     ▲
                                     │ 하네스 (이 템플릿)
                                     │ - .claude/agents
                                     │ - .claude/commands
                                     │ - .claude/hooks
                                     │ - .claude/skills
                                     │ - .claude/settings.json
                                     │ - .claude/CLAUDE.md
```

**하네스(Harness)**: AI가 엉뚱한 방향으로 가지 않도록 잡아주는 가이드라인 파일들의 묶음. 강아지 산책줄과 같은 역할.

## 폴더 구조와 책임

| 경로 | 책임 |
|------|------|
| `.claude/CLAUDE.md` | 1순위로 읽히는 프로젝트 헌법 (200자 이내, 핵심만) |
| `.claude/settings.json` | 권한(`allow`/`deny`) + 훅(`PreToolUse`, `PostToolUse`, `Notification`) |
| `.claude/agents/` | 백그라운드에서 도는 전문 작업자. 결과만 보고 |
| `.claude/commands/` | `/명령어` 단축키. 자연어 호출 실패 방지 |
| `.claude/hooks/` | 작업 전/후에 끼어들어 검증·차단하는 스크립트 |
| `.claude/skills/` | 대화창에서 직접 실행되는 절차서. 투명하지만 컨텍스트 사용량 큼 |
| `src/tokens/` | 디자인 토큰 (CSS 변수). **유일한 진실 원천**. 직접 수정 금지 |
| `src/components/ui/` | 컴포넌트. 반드시 토큰만 참조 |
| `docs/` | QA 리포트, 디자인 리뷰, diff 이미지 저장소 |
| `scripts/` | CI/유틸 스크립트 (스크린샷, 빌드 등) |

## 표준 워크플로우

### 신규 컴포넌트 만들기
1. 디자이너가 Figma에서 컴포넌트 디자인 확정
2. 노드 우클릭 → `Copy link to selection`
3. 개발자가 `/implement-figma <링크>` 실행
4. `figma-implementer` 에이전트가 토큰을 사용해 컴포넌트 코드 생성
5. `/qa <링크>` 로 시안 대비 일치 여부 검증

### 디자인 변경 반영
1. 디자이너가 Figma Variables(토큰) 변경
2. `/build-tokens <토큰 페이지 링크>` 실행 → `src/tokens/` 자동 갱신
3. `/check-tokens` 로 정합성 재확인
4. 영향받는 컴포넌트는 자동으로 새 토큰 값을 따라감 (CSS 변수의 힘)

### 릴리즈 전 검증
1. `/qa` 로 전체 컴포넌트 QA 리포트 생성
2. `/design-audit` 로 접근성·일관성 추가 점검
3. `docs/` 에 저장된 리포트를 PR에 첨부

## 핵심 원칙

1. **토큰은 단일 진실 원천**  
   디자인 값(색, 크기, 간격)은 `src/tokens/` 한 곳에서만 정의. 컴포넌트는 `var(--color-brand-500)` 처럼 토큰만 참조.

2. **하드코딩 자동 차단**  
   `#FF0000`, `16px`, `bg-red-500` 같은 패턴은 훅이 자동으로 거부. 토큰 우회 불가.

3. **큰 작업은 에이전트에 위임**  
   대화창 컨텍스트는 비싼 자원. 에이전트가 백그라운드에서 처리하고 요약만 보고 → AI 성능 유지.

4. **검증은 코드처럼 다룬다**  
   QA 결과는 마크다운 파일로 저장 → PR 리뷰 가능, 히스토리 추적 가능, diff 비교 가능.

## 사용자별 가이드

| 역할 | 주로 다루는 것 |
|------|---------------|
| **디자이너** | Figma Variables 관리, 컴포넌트 노드 링크 공유 |
| **프론트엔드 개발자** | `/implement-figma`, `/qa` 명령으로 코드 생성·검증 |
| **테크리드** | `.claude/agents/`, `hooks/` 커스터마이징. 회사 규칙 코드화 |
| **PM/QA** | `docs/` 의 리포트로 릴리즈 품질 확인 |
